# 状態を持つ処理のレビューの型

2026-09-08、PR #129（AlertTriage `/sweep`）で人のレビューが must 4 件を出し、こちらのローカルレビューは 1 件も拾えなかった。
原因は関数単位で差分を読んで満足し、複数回の実行をまたぐ場面を追わなかったこと。
再発防止として、対象に当てはまる差分では下の型を必ず踏む。

## 対象

差分が次のどれかに触れていたら対象（1 つでも当てはまれば全部やる）。

- 再試行（Scheduler / キューの retry、`--max-retry-attempts`、5xx で再実行）
- 時間の窓（lookback、日次、`ScheduleTime`、expiry / stalled 判定）
- 上限（cap、max fires、ページ数上限、打ち切り）
- 人の介入（人が付けるリアクション・ラベル・状態、機械と人が同じ印を使う）
- 外部 API の失敗（Slack / GitHub / Cloud Logging の読み取り・書き込み）

## 「レビュー済み」と言う前にたどる 5 シナリオ

各シナリオを実行順にたどり、「何が起動するか／何が数えられるか／何を返すか」を 1 行ずつ書き出す。
**書き出せないシナリオが 1 つでもあれば未レビュー**（「読んだ」を「レビュー済み」と言わない）。

1. **1 回目 → 途中で失敗 → 再試行**（同じ入力で 2 回目が走る）。二重起動・取りこぼしが出ないか。1 回目に付けた印が 2 回目の判定をどう変えるか
2. **日をまたぐ**（次回の窓）。今回の窓の端で処理した／しなかったものが、次回の窓でどう見えるか。窓の境界と expiry の重なり（窓の外に出る前に expiry が来るか）
3. **上限で余る**。cap に当たった残りを誰がいつ拾うか。上限到達を成功（200 / 正常終了）扱いにしていないか
4. **人が印を付ける／外す**。人が付けた状態を機械が消せるか。消せないときにカウント（reopened 等）や次回の判定が狂わないか
5. **外部 API が失敗する**。読み取り失敗・書き込み失敗のそれぞれで、呼び出し側が「スキップ（処理済み）」と区別できるか。区別できずに `continue` → 正常終了になっていないか

## 読み方

- **boolean を返す状態操作（`claimX` / `removeX` / `tryX` / `markX`）は、false の意味を全列挙してから読む。** 「失敗」と「すでに処理済み」が同じ値に潰れていたら、それ自体を指摘にする（呼び出し側が再試行に回せない）
- **前の巡で見たコミットも対象。** 毎回 base..head の全差分を読み直す。「前回レビュー済み」の部分にこそ、今回の変更と組み合わさって壊れる箇所がある
- **design.md / 既知の制約の一覧を「網羅されている」と信用しない。** 上の 5 シナリオを制約一覧と突き合わせ、書かれていないものを指摘候補にする
- **review-runner / code-review に投げるときは、この 5 シナリオをプロンプトに書いて渡す。** review-runner はこのファイルを自分では読まない。差分に対象語（retry / lookback / cap / reaction / expiry 等）があれば、シナリオごとに「何が起きるか」を返させる
- グループ化して 1 件にまとめる処理（summary / digest）は、**まとめの境界の印がどこに付くか**と、再試行で境界の印が付いた要素が除外されたあと残りがどう見えるかを追う
