# handoff: 確かめた事実だけで引き継ぎ、再開時に確かめ直す

引き継ぎファイルは、次のセッションがそのまま信じて動く唯一の材料になる。
だから中身は、書く時点で確認コマンドを流して得た結果だけで作る。
読む側は、同じコマンドを流し直してから作業に入る。

「引き継ぎを読んで」「〜の続き（引き継ぎがある作業を指すもの）」は「読む」、それ以外の呼び出しは「書く」で動く。
どちらか決められないときは、どちらをするかをユーザーに聞く。

## 書く

### 1. 対象を挙げる

このセッションで触ったものを会話から全部挙げる。
リポ・ブランチ・worktree・PR・CI・memory・外部のページ（Notion / Slack 等）・サブエージェントとバックグラウンドの処理。
前任のメモや自分の記憶にある主張（「push した」「CI は通った」等）も対象に入れる。
確かめる途中で見つかった、触った覚えのないもの（未追跡ファイル等）も対象に入れる。

### 2. 1 つずつ確かめる

| 対象 | 確認コマンド |
|---|---|
| リポ | `git -C <path> status --short --branch` / `git -C <path> fetch -q && git -C <path> log @{u}..HEAD --oneline`（fetch しないと手元の追跡ブランチが古いまま比べてしまう。上流が無ければその出力を結果にする）/ `git -C <path> worktree list` / `git -C <path> stash list` |
| 未コミットの差分 | `git -C <path> diff HEAD -- <file>` で中身を読み（`git diff` だけだと stage 済みの変更が見えない）、何の変更かを 1 行にする |
| 未追跡ファイル | `cat <path>/<file>` で中身を読み、何のファイルかを 1 行にする |
| PR | `cd <path> && gh pr view <番号> --json state,reviewDecision,statusCheckRollup` |
| CI | `cd <path> && gh run list --branch <branch> -L 3`（PR があれば上の `statusCheckRollup`） |
| 表に無い主張（「a.txt をコミットした」等） | 主張を裏づける読み取りコマンドを自分で決める（`git show --stat <rev>`・`git remote -v` 等） |
| サブエージェント・バックグラウンド | 完了通知を受け取ったか |
| 外部のページ | 読み取りツールで再取得 |

中身を読むコマンド（`git diff`・`cat`）は確かめるために流すだけで、「現在の状態」の確認コマンドには書かない。
「現在の状態」には `git -C <path> status --short -- <file>` のように中身を出さないコマンドを書く（読む側が流し直したときに中身が文脈へ出ないようにする）。

結果がまだ出ていないもの（CI 実行中・返事待ち）は、今の状態がそのまま確認結果になる（例: `gh run view 123` → in_progress）。
確認先が無いこと（リモート未設定・PR 未作成）も、そのエラー出力が確認結果になる。

確認コマンドは、そのままコピーして流せる形で書く（`<repo>` のような置き換えを使わず、`~` 始まりか絶対パス）。
差分やファイルの中身そのものは貼らない（認証情報が混ざりうる）。
前任メモと事実が食い違ったら、ファイルには今の事実だけを書き、食い違いはユーザーへの報告に書く。

### 3. 各項目を 3 つの欄のどれかに振り分ける

| 欄 | 入るもの | 1 行の形 |
|---|---|---|
| 現在の状態 | コマンドで確かめた事実 | `<事実> — \`<確認コマンド>\` → <結果>`（事実だけ。理由や前任メモの訂正は混ぜない） |
| 判断待ち | ユーザーにしか決められない・答えられないこと（誰が・なぜ入れたか、残すか消すか、意図どおりか） | `<問い>？ — <判断材料の所在>`（問いの形で書く。「不明」と書かない） |
| 次の一手 | 再開して最初にやること | `<やること>`（判断待ちの答えが要るなら「判断待ち N の回答を受けてから」を頭に付ける） |

「確かめていないこと」の欄は作らない。
コマンドで確かめられることは確かめて「現在の状態」へ、コマンドで答えが出ないことは「判断待ち」へ入れる。
どちらにも入らない項目は、手順 2 に戻って確認コマンドを決める。

### 4. 書く

作業中プロジェクトの memory ディレクトリ（system prompt の Memory 節のパス）に `handoff-<テーマ>.md` で書く。
テーマは kebab-case の短い語（例: `handoff-harness.md`）。
同じテーマのファイルがあれば上書きする（日付つきの新規ファイルを作らない。古い引き継ぎが残って食い違う）。

```markdown
---
name: handoff-<テーマ>
description: <テーマ>の引き継ぎ（YYYY-MM-DD 時点）。再開時は handoff skill の「読む」で確認コマンドを流し直してから作業する
metadata:
  type: project
---

## 現在の状態（YYYY-MM-DD HH:MM 確認。確認コマンドを最初に流した時刻）
- feat/x は未 push — `git -C ~/src/foo fetch -q && git -C ~/src/foo log @{u}..HEAD --oneline` → `fatal: no upstream configured`

## 判断待ち
- settings.json の `permissions` 追加は誰がなぜ入れたか、残すか戻すか？ — `git -C ~/src/foo diff settings.json`

## 次の一手
- 判断待ちの回答を受けてから push 先を決める
```

`MEMORY.md` に `- [<テーマ>の引き継ぎ](handoff-<テーマ>.md) — <hook>` を 1 行置く（既にあれば書き換える）。

### 5. 走査して読み直す

```bash
rg -n 'と思う|はず|おそらく|たぶん|と思われる|らしい|未確認|不明|<[^>]+>' <memoryディレクトリ>/handoff-<テーマ>.md
```

0 件になるまで、該当項目を手順 2 に戻して書き直す。
最後にファイルを Read で読み直し、手順 1 の対象が全部どこかの欄に載っていることと、索引の 1 行を確かめる。

### 6. 報告する

グローバルルールの「完了と言う前の 3 行」で締める（変えたもの＝引き継ぎファイルと索引のパス、確かめ方＝手順 5 の走査と Read の結果）。
前任メモと事実の食い違いがあれば、ここで併せて書く。

## 読む

急ぎの依頼や「聞かないで進めて」と言われたときも、手順 2〜5 は省かない（引き継ぎを書いたあとに状態が変わっていることがある）。

1. `MEMORY.md` から `handoff-<テーマ>.md` を探して読む。テーマが言われていない・候補が複数あるときは、一覧を示してどれかを聞く。見つからなければ、memory はプロジェクト（作業ディレクトリ）ごとに分かれているので `fd -I 'handoff-.*\.md' ~/.claude/projects` で他のプロジェクトも探す（worktree で書いた引き継ぎは別のディレクトリにある）。それでも無ければ「引き継ぎファイルが無い」と報告して止まる。
2. 「現在の状態」の確認コマンドを全部流し直す。流すのは読み取りのコマンドだけにする（`git status`・`git log`・`git fetch`・`gh pr view` 等）。書き込みや外部送信を伴うコマンドが混ざっていたら流さず、報告に書く。置き換え（`<repo>` 等）や推測語が残っていたら、ファイル内の定義から実際の値に直して流し、残っていたことを報告に書く。
3. 書いてある結果と今の結果を突き合わせる。結果が示す状態が同じなら一致とする（エラー文の言い回しの差は数えない）。食い違いを説明するのに要る読み取りコマンド（`git show` 等）は追加で流してよい。
4. 作業に入る前に報告する。
   - 食い違いがあれば、項目ごとに「引き継ぎ時 → 今」を 1 行で書く。無ければ「全項目一致」と 1 行で書く
   - 「判断待ち」を今の状態に合わせて問いを直してから示す
5. 食い違いがあったときは、ユーザーの返事を受けるまで書き込み（コミット・push・ファイル編集・外部への投稿）をしない。食い違いが無ければ「次の一手」から再開する。ただし判断待ちの答えが要る部分は、答えを受けるまで進めない。
6. 引き継ぎファイルは読むだけで直さない。セッションを終えるときに「書く」で上書きする。
